## 1. Lean 依赖：用远程检索接口替代本地预编译 (2026-09-16)

- 备选方案：mathlib 的 olean 缓存（`lake exe cache get`）、远程构建机、容器化预编译镜像。

## 2. 知识库规模化后的预编译体积 (2026-09-16)

**状态：** 待调研（只记录，暂不行动）

**问题：** 如果 AgtXIv 真的作为知识库建立起来，并且要和 mathlib、PhysLib 等多个 Lean 库结合，预编译产物会不会大到不可维护？

**初步判断（待验证）：**

- 体积的大头几乎肯定是 **mathlib 本身**，不是叠加的库。PhysLib 这类领域库相对 mathlib 是小量级，加进来是边际成本，不是翻倍。
- 真正会无界增长的不是「库」，是 **记录（records）**。知识库的增长在记录数上，而记录是**引用**库里的定义，不是复制。所以：
  - 如果记录只存「指向某个 Lean 定理的引用 + 元数据」→ 编译成本与知识库大小基本无关，只与依赖的库个数有关（近似常数）。
  - 如果每条记录自带需要重新类型检查的 Lean 证明 → 编译成本随记录数线性增长，这才是会爆的情形。
  - **这是一个架构选择，值得早点定下来。**
- 第二个真实痛点不是体积而是 **版本对齐**：mathlib + PhysLib + AgtXIv 自己那层，各自 pin 到不同的 Lean toolchain 版本时，升级会非常痛。依赖的库越多越痛。

**待确认：**
- PhysLib 及其他候选库的实际体积 / 维护活跃度 / toolchain 版本。
- AgtXIv 的记录是「引用型」还是「自带证明型」？（见上，决定成本是常数还是线性）
- 若是自带证明型：能否做增量验证（只重检改动的记录），而不是全量重编译。
- 与第 1 条合并考虑：检索走远程、验证走 CI 缓存，可能同时解决体积和内存两个问题。

## 3. 根本解法：验证是一次性事件，不是每次构建重新成立的性质 (2026-09-16)

**状态：** 构想，未验证可行性

**根源诊断：** Lean 检查证明分两步，成本差很多：
1. **Elaboration（精化）**——展开简写、`simp`、类型类推断，得到完整证明项。慢、吃内存、需要完整环境。
2. **Kernel checking（内核检查）**——用几千行的小内核验证证明项合法。便宜得多。

痛的是第 1 步，但**真正的信任只来自第 2 步**。把两者绑在一起是全部麻烦的来源。

**核心观念转变：** 现在的默认心智是「这条记录正确」=「我现在能重新编译通过它」，于是每人每次 CI 都在重付全部代价。改为：记录携带**证明凭证（attestation）**——

> 这条记录在 toolchain X + mathlib@rev Y 下于某时验证通过，证明项哈希为 Z。

凭证存在且签名后，**无人需要再验证**。读知识库不需要装 Lean；想独立核查的人拿导出的证明项用小内核重检（跳过昂贵的 elaboration）。成本从「每次 × 每人 × 全量」压到「每条记录一次」。

**三个配套机制：**
- **内容寻址 + 增量**：每条记录按其依赖闭包哈希。改一条只重验它和真正依赖它的记录。绝大多数记录彼此无关 → 实际重验量稀疏，不是线性。这是让成本 sublinear 的关键。
- **Epoch（快照纪元），不追最新**：知识库有若干冻结 epoch，每个固定一套 (Lean toolchain, mathlib rev, PhysLib rev)。记录标注自己在哪个 epoch 下验证。升级 epoch 是批量迁移任务（可跑很久、可有失败清单），不是日常负担。把持续的隐形成本变成偶发的显式成本。
- **联邦化，不自己托管库**：只存引用和哈希，不存 mathlib 副本、不负责编译它。上游提供预编译产物（`lake exe cache get` 即此思路）。只对自己那一层负责。

**影响：** 第 2 条的「引用型 vs 自带证明型」分叉不必二选一——可以自带证明，但**离线验证一次、在线只存凭证**，体积和内存不再随知识库增长。

**代价（要如实接受）：** 需设计凭证格式、维护 epoch 迁移、并接受信任模型是「过去某次验证 + 签名」而非「我现在亲手编译了一遍」。这是真实的信任弱化，虽与整个软件供应链的通行做法一致。

## 4. 项目定位：「测量」与「轶事」的区别 (2026-09-16)

**状态：** 定位陈述（framing），非待办

整个项目的目的，是希望**科学探索和验证不要变成随机过程**。

这是「测量」与「轶事」的区别：
- **轶事**：不可复现、无误差条、无出处、无法与他人的结果对齐。有人做过、有人觉得对。
- **测量**：有明确条件、可复现、可追溯、可被他人独立核验并接入自己的工作。

科学文献目前大量以轶事的形态在流通——结论可读，但其成立条件、依赖链、可核验性都不在其中。AgtXIv 要做的是把这部分补上，让一条科学主张具备被当作「测量」对待的资格。

**与技术设计的关系（这条不是空话，它直接约束前三条）：**
- 第 3 条的 attestation 本质上就是**测量记录**：在什么条件下（epoch = toolchain + 库版本）、由谁、何时、得到什么结果。凭证格式必须明确记录条件，否则它退化成轶事。
- epoch 的作用相当于**标定（calibration）**：没有它，两条记录的「验证通过」互相不可比。
- 内容寻址与依赖闭包相当于**给出误差传播路径**：一条结论依赖什么、上游变动会波及什么，必须是可计算的。

**判据：** 任何设计决策都可以拿这条来问——「这让结果更像测量，还是更像轶事？」

## 5. 成本估算：对一篇论文的所有 MathClaim 跑完 schema v0.2 (2026-09-17)

**状态：** 已降级 —— 见第 7 条决定：先跑通，降费后置。本条的估算模型保留待用，但不作为当前阻塞项。

### 先说一个口径问题

v0.2 README 明确写着：Lamport→Lean 分支 **只对一条选定的 MathClaim** 运行（"operates on one selected MathClaim only"，且 "There is no whole-paper autoformalization operation"）。所以「对所有 math claim 跑完 v0.2」**不是 v0.2 的默认路径**，而是一个扩展场景。估算时要分开两个口径，否则数字会差一个量级：

- **口径 A（v0.2 规格内）**：extract 全文 + dependency 逐条 claim + 形式化 **1 条** claim。
- **口径 B（本条问题）**：extract 全文 + dependency 逐条 + 形式化 **每一条** claim。

### 估算模型（参数化，数字待实测替换）

四个 operation，逐个拆 input / output：

| Operation | 频次 | 单次 input | 单次 output | 备注 |
|---|---|---|---|---|
| `paper.extract` | 每个 chunk 一次，约 10 chunk | ~11k（spec ~8k + 正文 chunk ~2k + 去重上下文 ~1k） | ~2k | spec 部分高度可缓存 |
| `dependency.search` | 每条 claim ~2 轮 | ~12k（spec ~5k + claim + host 检索回来的上游材料，**方差最大项**） | ~2k | host 在任务之间做实际检索 |
| `autoformalization.lamport` | 每条 claim，含重试 ~2 次 | ~9k | ~5k | 结构化证明，输出偏长 |
| `autoformalization.lean` | 每条 claim，含迭代 ~4 次 | ~15k（含固定环境/mathlib 片段） | ~4k | **成本大头**，迭代次数是主导因素 |

**每条 claim 的形式化成本** ≈ 100k in / 30k out（dependency + lamport + lean 合计）。

### 初步数量级（假设一篇理论论文 ~25 条 MathClaim）

- **口径 A**：extract 110k in / 20k out + dependency 25×24k = 600k in + 形式化 1 条 78k in
  → **约 0.8M input / 0.2M output**
- **口径 B**：extract 110k + 25 条 × 100k
  → **约 2.6M input / 0.8M output**

开 prompt caching（spec 部分约 8k × ~100 次调用重复）可省下大约 0.6M input，口径 B 降到 **~2.0M 有效 input**。

### 主导成本与敏感度（真正该先测的）

1. **`autoformalization.lean` 的迭代次数**——占口径 B 的一半以上。4 次 vs 10 次直接决定总量翻不翻倍。**这是第一个该实测的量。**
2. **MathClaim 条数**——线性因子。25 条是猜的，不同领域论文差很多。
3. **host 喂给 dependency / lean 的上游材料体积**——方差最大，取决于检索策略给多少上下文。
4. spec payload 是否走缓存——影响约 25%。

### 待做

- 不要整篇估。先拿 `examples/paper-minimal` 或一篇真论文的**一节**，实跑一次，量出上面四个参数的真实值，再线性外推。
- 单价换算另算：需要查当时的 model 价目表，不要用记忆中的价格。
- 注意与第 3 条呼应：lean 分支的迭代成本正是「验证只做一次、结果存成凭证」要摊销掉的东西。

## 6. PPT 素材：用「同一 query、不同模型、不同理解」铺垫流程规范的必要性 (2026-09-17)

**状态：** 待制作（demo 未跑，素材未采集）

### 设想

在 PPT 中并排展示不同模型调用对同一 query 的不同理解，作为 AgtXIv 流程规范的动机铺垫：

1. **query A：`how to understand this paper`** —— 展示不同模型给出的「理解」在关注点、粒度、结论上分叉。结合 Tobias 的 talk 一起讲。
2. **query B：`please formalize this proof`** —— 展示这条指令本身的模糊性。

### 为什么这个 demo 有力（与第 4 条的关系）

这正是「测量 vs 轶事」的**可视化**。同一输入、未规定条件、输出发散——这就是科学探索变成随机过程的字面演示。观众不需要被说服，他们直接看见。

**叙事弧：** 发散（问题）→ 模糊性拆解（诊断）→ v0.2 的 Task 字段（解法）。

### query B 的模糊性拆解 —— 这是承上启下的关键一页

`please formalize this proof` 没有回答的问题：

- **哪一条 claim？** 一篇论文里的 proof 往往含多个待证命题。
- **在什么环境下？** 哪个 Lean toolchain、哪个 mathlib rev？（= 第 3 条的 epoch）
- **什么算做完？** 能编译？没有 `sorry`？还是所有引用的引理都已存在？
- **允许假设什么？** 哪些上游结论可以直接引用而不展开？
- **目标形式是什么？** 直接出 Lean，还是先过 Lamport 结构化中间件？

**payoff：** 把这张「模糊性清单」和 v0.2 的 Task 必填字段并排放——**清单的每一项，恰好就是一个字段**。规范不是凭空发明的官僚流程，而是这些问题被迫回答之后的残留物。这一页把「创新」讲成「必然」，比宣称新颖更有说服力。

### 制作时的自我约束（重要）

demo 本身必须是**测量**而不是轶事，否则台下第一个问题就会打穿它：

- 各模型用**完全相同**的 prompt 和输入文件。
- 标注模型名、版本、调用日期、温度等参数。
- 如实说明是否挑选过输出（cherry-picking）。若展示的是多次采样中的代表性样本，说明采样次数。
- 分叉要是**真实的实质分歧**，不是措辞差异。

### 待确认

- **Tobias 的 talk 具体是哪一个？** 需要标题/出处/要引用的具体论点——我手上没有这个信息，不要凭空复述。
- 选哪篇论文做 demo（用听众熟悉的，分叉才有冲击力）。
- 用几个模型、并排几栏（建议 3 栏，超过就看不清）。
- 是否录屏实跑，还是静态截图（实跑更可信但有风险）。

## 7. 优先级决定：先跑通，再考虑降费 (2026-09-18)

**状态：** 已决定

**决定：** 先把 v0.2 端到端跑通，成本优化（第 5 条）后置。

**理由：**

- 目前已知的首要问题是各层之间**跑不通端到端**，不是跑得太贵。在没有一条完整链路之前，成本数字没有可优化的对象。
- 第 5 条本身也指向同一结论：那份估算被 `autoformalization.lean` 的迭代次数单一参数支配，而这个参数**只能靠实跑测出来**。先降费等于在猜一个未知量上做优化。
- 降费手段（prompt caching、缩减 spec payload、减少迭代、裁剪上游材料）几乎都会改变输出质量或 Task 语义。在基线尚未建立时引入这些，会让「跑不通」和「被优化坏了」无法区分。**先要一条能用来对照的基线。**

**推论（对当前工作的约束）：**
- 第一次跑通**允许昂贵**——全量 spec、不开缓存、放宽迭代上限。目标是「有输出且可检查」，不是「便宜」。
- 但跑通时要**顺带记录** token 用量（尤其是 lean 分支的实际迭代次数），这样第 5 条的估算可以直接用真实数据填，而不必为此另跑一轮。
- 重新开启降费的触发条件：端到端跑通一次并留下可对照的输出之后。

## 8. 降费手段：受约束的类型化输出（typesafe.ai / jev 的思路） (2026-09-18)

**状态：** 待调研（按第 7 条，降费后置；但这条要先记着，因为它可能影响跑通阶段的接口设计）

**想法：** 让模型输出固定的 type（受 schema 约束的结构化输出），而非自由文本再解析，以节约大量 token。参考 typesafe.ai 这个网站，以及 jev 的思考方式。

### 与 v0.2 已有设计的接口

v0.2 已经有五个 machine schema（`common` / `items` / `output` / `run` / `task`），其中 `output.schema.json` 就是「模型该输出什么类型」。所以这条**不是引入新概念，而是换一种执行方式**：

- 现在（隐含）：模型自由生成 → 事后校验 → 不合格则重试。
- 提议：在解码阶段就约束到 schema，使不合法输出根本无法生成。

规格已经写好了一半——缺的是 enforcement 的位置。

### 省在哪里（要说准，别高估）

- **直接省 output token**：不生成解释性散文、不重复 schema 脚手架。但按第 5 条，output 只有 ~0.8M，而 input 是 ~2.6M，所以**直接节省是较小的那一侧**。
- **真正的大头是消灭重试**：每次输出不合法而重试，都要**把整个 prompt 重发一遍**。一次失败的 lean 迭代就是 ~15k input 白付。第 5 条已经指出迭代次数是支配全局的参数——所以类型化输出是**间接打在主导杠杆上**，这才是它值钱的地方。
- **不省 input**：约束解码对输入侧没有帮助，别把两者混为一谈。

### 需要小心的地方

- 受约束解码可能**降低推理质量**：强行禁止模型先写推理再给结论，某些任务上会变差。对 `paper.extract` 这类抽取任务大概率无害；对 `autoformalization.lamport` 这类需要推理的任务要实测。
  - 常见折中：允许一个自由的 reasoning 字段 + 其余字段受约束。
- 与第 7 条的关系：**跑通阶段不要为了省钱上这个**，但要确保跑通时的接口不排斥它——即模型输出走 `output.schema.json`，不要中途引入临时的自由文本格式，否则事后接入受约束解码要返工。

### typesafe.ai 是什么（2026-09-18 查证，来源：https://typesafe.ai/ ）

**关键澄清：Jev 不是人，是他们的模型。** 「jev 的思考方式」指的是这个模型的工作范式。

- 公司做的是**面向软件自动化的 machine-native 模型**，不是对话模型。旗舰产品 **Jev**，自称 "System One Model"。
- 它**不生成文本**，而是产出 **"typed decisions with calibrated probabilities"**（带校准置信度的类型化决策），软件可直接据此行动。
- 技术组成（其自述）：新模型架构 + 自定义 sampler + **RLCD**（Reinforcement Learning for Calibrated Decisions，其 RLHF 替代方案）。
- 宣称：System One 任务上比 LLM 工作流 **193.6x faster / 444.6x cheaper**；input 定价 **$42 / 十亿 token**；"Zero Hallucinations"（靠置信估计）。
- 页面标注 "Made in SF"、版本 **0.01**，未列出团队姓名。联系方式 hello@typesafe.ai。

### 这对 AgtXIv 意味着什么（比单纯「省 token」更有用的读法）

Jev 的定位是 **System One**——快、便宜、类型化、带置信度。它**不是**用来替代需要推理的环节的。真正的启发是**把 v0.2 流水线按 System One / System Two 切开，只对后者付 LLM 的价钱**：

- **适合 System One 的子任务**（分类、路由、过滤、判定）：候选项是否属于某个类别、某段文字是否含 MathClaim、检索回来的上游材料是否相关、lean 输出是否需要再迭代。这些目前可能都在用大模型做，而它们本质是**带置信度的分类**。
- **必须留给 System Two 的**：`autoformalization.lamport`、`autoformalization.lean` 的实际证明构造。这些是第 5 条里的成本大头，Jev 替代不了。
- **潜在杠杆**：如果 System One 部分能承担「筛掉不必进入昂贵环节的候选」，它削减的是**昂贵调用的次数**，而不只是单次调用的价格。这比第 8 条原本设想的「省 output token」量级大得多。

**与第 4 条的呼应：** calibrated probability 在形态上比裸断言更接近「带误差条的测量」。如果置信度真的校准，它可以直接进 attestation 作为一个可比较的量。**但这需要独立验证，不能采信厂商自述。**

### 保持怀疑的地方（如实记录）

- **"Zero Hallucinations" 是营销话术**。置信估计不消除错误答案，只是给它贴标签。低置信的错答仍然是错答。要看的是校准曲线，不是这句宣称。
- 版本 **0.01**、无团队署名、无独立基准——数量级宣称（444.6x、238x）需要自己在自己的任务上复现才算数。
- 对比基准是「LLM-based workflows for System One tasks」，即**挑选过的有利任务类别**。不能外推到 lamport / lean 这类任务。

### 待确认

- 实际可用性：有无公开 API、定价是否对外、0.01 版的稳定性。
- 支持的类型表达能力：v0.2 的 `output.schema.json` 是否落在其可表达范围内（递归、union 常是踩坑点）。
- 拿一个真实子任务（建议「某段文字是否含 MathClaim」）做小规模对照，量出准确率和校准度，再决定是否引入。
- 目标模型自身是否已原生支持 structured outputs / JSON schema 约束——若够用，可能不必引入外部依赖。
