# AgtXIv v0.3 → v0.4 Architecture Changes

This note records why the 2026-08-18 specification is a structural revision rather than a copy-edit. The previous v0.3 snapshot remains available at [`docs/archive/specifications/AgtXIv-v0.3-2026-08-17.md`](../archive/specifications/AgtXIv-v0.3-2026-08-17.md).

## Summary

Version 0.4 turns the earlier mathematics-centered protocol into a multi-view, verification-driven architecture. It keeps the core safety rules—source grounding, non-promotion of Oracle output, query-relative closure, explicit unresolved frontiers, and separate verification axes—but makes the graph, alignment, repair, and release interfaces more precise.

## 1. Three system-level graphs replace an overloaded dependency graph

- `PaperInteractionGraph` is a global, typed literature graph and may contain cycles.
- `MathClaimDependencyDAG(q)` is the strict, query-relative mathematical build graph.
- `PaperBuildDAG(q)` is derived by projecting accepted claim dependencies to papers and condensing paper-level strongly connected components.
- Explicit `InferenceStep` nodes preserve the joint semantics of multi-premise inference without requiring a dedicated hypergraph database.

This separates paper interaction from mathematical dependence: reciprocal paper relations no longer imply a circular proof.

## 2. Candidate extraction is separated from accepted build structure

Version 0.4 makes the following boundary explicit:

```text
LLM extraction
→ constrained schema
→ source grounding
→ relation validation
→ candidate graph
→ verification-guided refinement
```

Oracle-proposed claims and edges remain candidates. Only accepted, source-grounded, typed dependencies may enter a build order.

## 3. Verification failures drive local graph repair

Failures are normalized into three top-level classes:

- `LOCAL_BUILD_FAILURE`
- `ALIGNMENT_FAILURE`
- `SOURCE_OR_FOUNDATION_GAP`

The corresponding repair actions—local expansion, rewiring/rescoping, or escalation/blocking—are recorded in `GraphRepairRecord` objects. The former fixed-point idea is therefore made operational and auditable.

## 4. Lean checking and source alignment become distinct layers

The formalization loop is now:

```text
frozen source
↔ MathClaimIR
↔ Lean declaration
↔ source-blind backtranslation
```

It adds package/declaration retrieval, an evolving blueprint, a source-blind backtranslator, an alignment auditor, and a source-aware refiner. A clean Lean build proves the encoded theorem from its encoded assumptions; it does not by itself establish that the encoding matches the source claim or intended physics.

## 5. The contract model expands

Version 0.4 introduces or strengthens:

- `ScientificClaim`
- `MathClaimIR`
- `CandidateRelation`
- `InferenceStep`
- `SemanticContract`
- `EvidenceRecord`
- `ReproductionRecord`
- `LeanPackageCapabilityRecord`
- `GraphRepairRecord`

The registry can now track extraction, relation evidence, formal alignment, semantics, reproduction, package reuse, and graph repair without collapsing them into one trust score.

## 6. Semantic and computational evidence are simplified

The pilot does not require a separate DAG for every evidence profile:

- physical interpretation, model assumptions, approximation regimes, operational definitions, and empirical support are represented in `SemanticContract`;
- numerical reproduction is an optional claim-attached `ReproductionRecord`;
- semantic alignment, approximation validity, empirical support, computation, and human review remain distinct status axes.

## 7. Product v1 receives a concrete vertical-slice plan

The [v1 implementation checklist](../roadmaps/v1-implementation-checklist.md) is not another specification version. It maps v0.4 to the Stabilizerness pilot and requires:

- one primary query that reaches `MATH_CLOSED`;
- one intentionally blocked secondary query;
- one false-claim negative control;
- at least one verification-driven graph repair;
- at least one source-blind backtranslation and alignment audit;
- a deliberately small claim closure.

## 8. Relationship to the mathematics-pipeline specification

The [mathematics pipeline](mathematics-pipeline.md) remains the normative detail for claim decomposition, Oracle search, Lean construction, proof-guided DAG optimization, fixed-point iteration, and reuse. Its graphs $G^O$, $G^S$, $G^L$, and $G^Q$ are lifecycle/evidence views, while v0.4's `PaperInteractionGraph`, `MathClaimDependencyDAG(q)`, and `PaperBuildDAG(q)` are system-level graph roles. The authoritative crosswalk is in [AgtXIv §2.2](../../AgtXIv.md#crosswalk-to-the-mathematics-pipeline-graph-views).

## Version and file policy

- [`AgtXIv.md`](../../AgtXIv.md) is the only current system specification.
- Specification versions use the document metadata and Git history, not `_v1`/`_v2` filename suffixes.
- Product release `v1` is tracked by the roadmap and must not be confused with specification v0.4.
- Historical documents and superseded visual drafts live under `docs/archive/` and are non-normative.
