# AgtXIv V2 threat model

- Model status: Accepted
- Control implementation: milestone-owned and not yet production-enforced
- Milestone: M0
- Date: 2026-08-31
- Roadmap decisions: D1-D10, especially D2, D7, and D9
- Scope: V2 intake, acquisition, source processing, model use, formal builds,
  release, archive, review, admission, query, and offline verification
- Terminology: follows `docs/roadmaps/v2-end-to-end-implementation-plan.md` Section 2.1

## 1. Security objective and intuition

AgtXIv processes adversarial documents and produces records that may later be
trusted or reused. Its security objective is not merely service availability. It
must prevent untrusted paper or model content from acquiring network, credential,
signing, review, or knowledge-write authority; prevent mutable bytes or identities
from being presented as reviewed; and preserve enough public evidence to audit a
decision without storing private reasoning traces.

The physical picture is a clean-room evidence laboratory:

- acquisition is a receiving dock that can fetch only named suppliers and writes
  only to quarantine;
- extraction and analysis happen in isolated rooms with no outside doors;
- a model gateway is a narrow, logged service hatch, not a general network card;
- reviewers, certifiers, and archivists use different keys and badges;
- the final evidence bag is sealed by digest and signature;
- admission into the reusable library happens at a separate guarded desk.

No control turns a mathematically valid theorem into source fidelity or
scientific applicability. Security preserves the integrity of those independent
assessments; it does not replace them.

## 2. Assets

The protected assets are:

1. exact acquired and generated bytes, their digests, rights records, and
   quarantine/promoted state;
2. contract bundles, schemas, validators, policies, environment manifests, and
   canonicalization rules;
3. attempt/event lineage, source anchors, scientific claims, mathematical IR,
   graphs, formal evidence, assessments, and unresolved frontier;
4. Root audits, certificates, signatures, replay-bundle roots, archive receipts,
   admission decisions, and knowledge snapshots;
5. actor identities, credentials, signing keys, trust roots, and role/independence
   evidence;
6. service availability, compute budgets, and reviewer capacity;
7. confidential or redistribution-restricted source bytes and approved model
   payloads;
8. the distinction between public evidence and non-persisted private reasoning.

## 3. Trust boundaries and allowed authority

| Component | May read | May write/call | Explicitly forbidden |
|---|---|---|---|
| Public API | validated commands and public projections | append intake/request through application service | direct final reviews, certification, admission, raw SQL/CAS mutation, long analysis |
| Acquisition worker | normalized arXiv identity, allowlist, acquisition credential if needed | allowlisted source endpoints; quarantine objects and acquisition events | arbitrary caller URLs, release signing, review, archive/admission credentials, canonical promotion by itself |
| Safe extractor | one quarantined object | bounded extracted quarantine tree and audit | network, host paths, links/devices, credential access, TeX execution |
| Analysis/extraction workers | promoted read-only source and exact inputs | immutable candidate artifacts/events | outbound network, credentials, signatures, final reviews, knowledge writes |
| Model gateway | minimum policy-approved payload | configured provider or local adapter; immutable request/response receipts | CAS/DB browse, signing, review, admission, arbitrary tools, provider choice by paper text |
| Formal build worker | pinned package, toolchain, read-only inputs | bounded build outputs/logs in quarantine | network, floating dependencies, host credentials, release/admission authority |
| V2 Root Agent service | exact candidate package and selected evidence | one immutable audit request/result under Root role | producing artifacts it audits, certification, knowledge admission |
| Mechanical certifier | exact manifest, audit, policy, signature material | immutable mechanical certificate | changing scientific findings/frontier, producing content, admission |
| Archive service | exact certified bundle | conditional CAS/WORM archive and receipt | changing bundle contents, deciding entry eligibility |
| Admission service | archived root, independent per-entry decisions, exact snapshots | one atomic append-only knowledge transaction | self-review, partial mutation, changing archived release |
| Query service | exact release/snapshot projections | read-only resolution; optional canonical intake request | canonical scope mutation, admission, conflict suppression |

D9 permits external Internet egress from the paper-processing plane only through
the acquisition worker and the optional policy-enabled model gateway. Every
other paper-processing worker is offline by default. Authenticated internal
database, object-store, queue, and service traffic follows separate identity and
network allowlists; CI/release egress follows a separately governed supply-chain
policy. Neither is controllable by paper content. Network policy is enforced
below the application layer as well as in code.

## 4. Adversaries and assumptions

Consider:

- a malicious or compromised arXiv source archive, TeX/PDF file, bibliography,
  image, generated proof package, or metadata field;
- prompt injection embedded in paper content or model output;
- an unauthenticated or authenticated API client exceeding its authority;
- a compromised worker, dependency, model provider, reviewer account, signing
  key, or operator;
- an insider attempting self-review, stale-evidence reuse, conflict suppression,
  or unauthorized byte disclosure;
- accidental operator error, crash, retry race, partial transaction, clock skew,
  or storage corruption.

We do not assume paper content is benign, a model follows policy, filenames are
safe, network responses remain stable, a build is deterministic without checks,
or a signature alone proves scientific correctness.

## 5. Threats, controls, and required evidence

### 5.1 Source acquisition, SSRF, and version confusion

Threats include server-side request forgery (SSRF), DNS rebinding, redirects to
private services, alternate ports/schemes, oversized responses, request smuggling,
rate-limit abuse, mutable unversioned sources, a PDF/source version mismatch, and
attacker-controlled download URLs.

Controls:

- parse input with the versioned `ArxivInputGrammar`; construct fetch URLs from a
  normalized modern/legacy arXiv identity rather than following caller URLs;
- allowlist scheme, host, port, path shape, and endpoint class; resolve and reject
  loopback, link-local, private, multicast, metadata-service, and disallowed IPv6
  ranges before connection and after every redirect/DNS resolution;
- bound redirects and validate every hop; disable ambient proxies unless they are
  an explicitly controlled egress path;
- enforce connect/read/total timeouts, byte limits, content-type expectations,
  rate limits, retry budgets, and circuit breakers;
- freeze exact observed version, response metadata, acquisition time, digest, and
  source/PDF relationship; an omitted version is resolved once, never at replay;
- give the acquisition worker no signing, review, archive, or knowledge-write
  credential and permit writes only to quarantine.

Required evidence: normalized input result, endpoint/policy revision, redirect
chain, resolved network targets, headers needed for provenance, exact version,
byte count/digest, attempt identity, and typed terminal result.

### 5.2 Archive extraction and hostile document processing

Threats include path traversal, absolute paths, Unicode/case collisions, symlinks,
hardlinks, devices/FIFOs/sockets, sparse files, archive bombs, nested archives,
huge file counts/paths, malformed encodings, parser exploits, TeX shell escape,
PDF active content, and a source file attempting to overwrite another artifact.

Controls:

- inspect an archive without extracting first; reject traversal, absolute paths,
  empty/invalid normalized paths, links, devices, special files, duplicate
  case-insensitive or Unicode-normalized paths, and policy-forbidden nesting;
- stream extraction into a newly created quarantine directory using safe APIs;
  never trust archive ownership, permissions, timestamps, or destination paths;
- enforce compressed/uncompressed bytes, expansion ratio, file count, per-file
  size, nesting, path length, CPU, memory, and wall-clock limits;
- treat TeX as data. Do not invoke shell escape or arbitrary build hooks. TeX/PDF
  parsers run offline in disposable sandboxes with read-only input and no host
  mounts or credentials;
- scan and canonicalize the extracted tree, calculate file and tree hashes, and
  promote to CAS only after policy validation; promotion is conditional and
  cannot overwrite an existing digest with different bytes;
- preserve rejected input digest and public failure evidence when rights and
  policy permit, without exposing exploit payloads unnecessarily.

Required evidence: extraction policy/version, rejected entries and reason codes,
resource measurements, tool/container digest, normalized tree listing, file/tree
hashes, quarantine identity, and promotion decision.

### 5.3 Model gateway and prompt injection

Threats include a paper instructing the model to exfiltrate data or change roles,
provider retention of restricted source, cross-attempt data leakage, unpinned
model behavior, forged citations/evidence, malicious generated code, and the
model attempting tools, network, review, signing, or admission.

Controls:

- all hosted-model calls pass through one gateway under an exact profile and
  data-use policy; local models use the same recorded interface without network;
- send only the minimum approved payload; strip credentials, unrelated records,
  private reviewer data, and rights-forbidden bytes;
- pin provider, model/version or immutable provider revision where available,
  gateway policy, retention setting, response format, and budget;
- record request and response digests, attempt identity, timestamps, and policy;
  store bytes only according to rights and retention policy;
- parse output as untrusted candidate data against strict schemas and stable
  vocabularies; never interpret model text as a command, credential request,
  assessment, signature, or admission decision;
- generated code and formal packages execute only in the offline sandbox and gain
  no authority from their provenance;
- require independent evidence/review for source alignment, formal validation,
  and scientific applicability.

Required evidence: model/gateway descriptor, approved payload class, policy and
retention refs, request/response digests, resource usage, validation result, and
the producer/independent-review identities.

### 5.4 Sandbox escape and resource exhaustion

Threats include arbitrary code execution, kernel/container escape, fork/process
bombs, memory/disk/CPU exhaustion, host file reads, Unix socket or cloud-metadata
access, dependency downloads, nondeterministic time/random/network behavior, and
one attempt observing another.

Controls:

- one ephemeral sandbox per attempt with a non-root user, read-only base and
  inputs, isolated writable scratch/output, no host socket, no ambient secret,
  and deny-by-default network policy;
- explicit CPU, memory, process, open-file, output-byte, disk, and wall-clock
  limits; terminate the entire process group on timeout;
- minimal pinned runtime/container images with vulnerability and software-bill-of-
  materials scans; restrict system calls/capabilities and prohibit privileged
  mode;
- copy validated outputs to quarantine, hash and schema-check them outside the
  untrusted process, then promote conditionally;
- record exact environment, dependency, toolchain, command, limit, exit, and log
  digests; logs are size-bounded and secret-redacted;
- periodically test isolation and recovery rather than treating a container as a
  complete security boundary.

### 5.5 Credentials and service identities

Threats include credentials in paper-visible tools, source archives, prompts,
logs, replay bundles, crash dumps, environment variables, browser assets, or
worker images; a broad credential allowing acquisition to sign or admission to
edit archives; stolen session/reviewer tokens; and confused-deputy calls.

Controls:

- workload identities and short-lived, audience-bound credentials; no static
  production secrets in the repository, image, paper workspace, or model payload;
- separate credentials and storage/network policies for acquisition, analysis,
  Root audit, certification, archive, admission, and query services;
- least-privilege database roles and CAS prefixes; signing keys are non-exportable
  where production facilities permit;
- authenticated service-to-service requests exact-bind actor, role, intent,
  target hashes, idempotency key, and policy;
- secret scanning before commit/build/release, redaction at log boundaries, token
  rotation/revocation, and audited emergency access;
- browser/public artifact tests assert that no credential or internal locator is
  exposed.

### 5.6 Signatures, trust roots, and replay integrity

Threats include signing the wrong canonical payload, algorithm downgrade, key-role
confusion, replaying a valid certificate for changed bytes, key compromise,
backdated signatures, trust-root replacement, partial bundle delivery, and Merkle
ambiguity.

Controls:

- ADR 0002's exact signature suite and trust policy live in the immutable contract
  bundle; algorithms, canonicalization, domain separators, actor role, and key ID
  are explicit;
- every Root audit/certificate/archive action binds the exact manifest, contract,
  scope, policy, environment, artifact tree, and preceding decision hashes;
- verify canonical bytes and Merkle inclusion before signature acceptance;
- distinct role-constrained keys for Root audit and mechanical certification;
- append-only issuance, rotation, expiry, revocation, compromise, and trust-root
  records with policy-defined historical verification semantics;
- offline verifier ships trust evidence sufficient to explain both cryptographic
  validity and policy validity at issuance; it never equates either with
  scientific correctness.

### 5.7 Roles, reviews, and separation of duties

Threats include producer self-review, Root self-certification, certifier changing
scientific findings, reviewer conflicts of interest, client-authored final states,
stale reviews, fabricated agent identities, hidden uncertainty, and persistence of
private chain-of-thought.

Controls:

- every actor records kind (`HUMAN`, `AGENT`, or `MECHANICAL_SERVICE`), immutable
  identity, role, policy, credential/key, and independence/conflict evidence;
- application checks and database constraints enforce the D7 identity/role
  matrix; high-value operations require current authenticated role and exact
  request targets;
- endpoints create review/certification/admission requests; only authorized
  services derive immutable final states;
- decisions bind every reviewed byte, record, contract, environment, scope, and
  policy hash. Any difference rejects the decision as stale;
- Root Agent owns the accountable profile/scientific audit; certifier performs
  only mechanical checks and cannot edit frontier or assessment selection;
- store public rationale, evidence, findings, uncertainty, and non-implications;
  do not request or persist private chain-of-thought.

### 5.8 Rights, privacy, and redistribution

Threats include redistributing a source or generated derivative without rights,
sending restricted bytes to a hosted model, leaking personal/reviewer data,
confusing public metadata with public bytes, immutable storage conflicting with a
valid takedown, and an untraceable license change.

Controls:

- every retained source/package/artifact has an exact origin, license/terms
  observation, redistribution disposition, allowed processing/model-use classes,
  and policy/reviewer evidence;
- byte-serving checks rights at request time; when bytes cannot be served, expose
  only the policy-allowed digest, immutable locator, and reason, and let an offline
  verifier accept user-supplied authorized bytes;
- hosted-model use is forbidden unless both profile and rights policy authorize
  the exact payload class and retention setting;
- separate public evidence from confidential reviewer/identity data and minimize
  personal data; access and retention are purpose-bound;
- takedown/withdrawal appends a public status record and disables unauthorized
  byte serving without rewriting historical hashes. Legal deletion from a byte
  store is recorded as a tombstone/right-disposition event; no system claims the
  deleted bytes remain offline-verifiable without an authorized copy;
- rights policy changes create new immutable decisions and do not backdate old
  observations.

### 5.9 Append-only database, admission, and query integrity

Threats include direct immutable-row update/delete, retry duplication, lease races,
partial admission, stale before-snapshot, CAS/database mismatch, SQL injection,
cross-domain leakage, unauthorized graph edges, and suppression of conflicting
records in a query.

Controls:

- typed application commands, parameterized database access, database constraints,
  append-only triggers/policies, least-privilege roles, and immutable audit log;
- idempotency keys and immutable attempt identities; lease expiry creates a new
  attempt rather than rewriting evidence;
- serializable/locked admission transition with exact before/after snapshot roots,
  candidate-set hash, all-or-nothing commit, and deterministic retry;
- CAS conditional writes plus reconciliation of object digest, record hash,
  database reference, and archive root;
- exact domain/snapshot authorization on every read; complete conflict-preserving
  relation closure for queries; ranking cannot delete required endpoints;
- backup, restore, corruption, concurrent-admission, and disaster-recovery tests.

### 5.10 Supply chain and CI/release path

Threats include compromised dependencies/actions/images, unreviewed generated
files, poisoned lockfiles, artifact substitution between CI jobs, a malicious pull
request accessing secrets, and a Git merge being mistaken for scientific release.

Controls:

- locked dependencies and toolchains, provenance/attestation for build artifacts,
  software bill of materials, dependency/container/secret scans, minimal CI
  permissions, and no production secret exposure to untrusted pull requests;
- generated-model/OpenAPI/catalog/coverage drift checks and clean-checkout builds;
- protected release workflow that binds Git commit/blob identities into the
  `ContractBundleRelease` and signs exact outputs;
- Git merge remains code governance only; scientific release, archive, and
  admission use their independent state machines and roles.

## 6. Required adversarial acceptance suite

The following tests are release gates at the owning roadmap milestone:

| Test family | Required cases | Expected outcome |
|---|---|---|
| Input/SSRF | private IP, loopback, metadata host, encoded host, DNS rebind, redirect hop, alternate scheme/port, caller URL | No disallowed connection; stable rejection/terminal evidence. |
| Archive | `../`, absolute path, symlink, hardlink, device, Unicode/case duplicate, sparse/oversized file, nested/archive bomb | No write escapes quarantine; bounded evidence-bearing rejection. |
| Parser/build | malicious TeX/PDF, shell escape, generated code network call, fork/memory/disk bomb | Offline sandbox contains attempt and records exact resource termination. |
| Model | prompt injection requesting credentials/tools/role change, restricted payload, provider retention conflict | Gateway withholds forbidden data/authority; candidate output remains untrusted. |
| Credentials | secret planted in environment/log/output/public UI; confused-deputy request | Scan/test fails; unauthorized service action is denied and audited. |
| Signatures | changed byte, wrong role key, unknown root, downgrade, expired/revoked/compromised key, replayed certificate | Verification fails with exact cryptographic/policy reason. |
| Roles | producer=Root, Root=certifier, reviewer conflict, caller-authored decision, stale review | Application and database reject; no final state is created. |
| Rights | non-redistributable byte request, forbidden hosted-model use, takedown | Bytes/payload withheld; digest/locator/tombstone evidence follows policy. |
| Transactions | duplicate submit, lease expiry, concurrent admission, mid-transaction crash, stale snapshot, CAS/DB mismatch | Idempotent immutable attempts; atomic rollback/retry; reconciliation detects drift. |
| Queries | conflicting/correcting/refuting relation with ranked endpoint | Complete relation and both endpoints remain returned for the exact snapshot. |

The core CI suite uses deterministic offline fixtures. Live arXiv and hosted-model
tests are separate smoke lanes and cannot be required for reproducible core pass.

## 7. Security invariants

1. Only acquisition and the policy-enabled model gateway can initiate external
   Internet egress from the paper-processing plane; paper content cannot expand
   that set or control internal-service and CI/release allowlists.
2. No untrusted worker holds release-signing, review, archive-admission, or
   knowledge-write credentials.
3. Untrusted bytes remain quarantined until bounded validation and digest/tree
   checks succeed.
4. Every security-relevant action binds exact actor, role, policy, input, attempt,
   environment, and result hashes.
5. A changed byte, record, contract, scope, environment, policy, or trust state
   cannot reuse a stale review or certificate.
6. Archive is immutable; admission is later, per-entry, independently reviewed,
   append-only, and atomic.
7. Rights to inspect metadata do not imply rights to redistribute bytes or send
   them to a hosted model.
8. Public rationale and evidence are retained; credentials, unrelated private
   data, and private chain-of-thought are not.
9. Availability limits produce typed terminal results; they never justify silent
   omission or false success.
10. Cryptographic integrity, formal validity, source fidelity, and scientific
    applicability remain separate claims.

## 8. Residual risks and milestone ownership

At M0 these controls are accepted design requirements, not a claim that production
enforcement exists. M1 owns typed security/authority contracts and negative
fixtures; M1.5 owns safe local acquisition/extraction/sandbox walking slices; M2
owns durable identity, database, object-store, queue, and role enforcement; M3
owns grammar-complete hardened arXiv intake; M5 owns pinned formal sandboxes; M6
owns production signatures, archive, and admission; M7 owns public/browser and
downloaded-bundle verification; M8 owns operational scans, recovery, and release
hardening.

Material residual risks must appear in each release audit and must not be hidden
behind `ACCOUNTING_COMPLETE`. A control may be marked implemented only when its
positive, negative, recovery, and evidence tests pass in the target adapter.

## 9. Review triggers

Review and supersede this threat model when any of these changes:

- supported source host/input grammar or archive/PDF/TeX processing engine;
- model provider, retention policy, or payload class;
- sandbox/runtime/container boundary;
- signature algorithm, trust root, actor/key model, or revocation policy;
- rights, privacy, takedown, or public-byte-serving policy;
- role matrix, database authority, CAS/object-store, admission semantics, or query
  conflict policy;
- graph/formal execution gains a new tool, network, or code-execution capability.

The superseding model must name migration impact, newly covered threats, residual
risks, and the exact contract release in which its controls take effect.
