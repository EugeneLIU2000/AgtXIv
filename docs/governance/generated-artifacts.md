# Generated artifacts and source-rights policy

## Purpose

Generated output is useful only when a reviewer can answer four questions:

1. Which exact inputs produced it?
2. Which exact producer and environment were used?
3. Can the result be regenerated or independently verified?
4. May the bytes legally and safely be stored or redistributed here?

“Generated” is not a scientific status. A generated formal file is not
kernel-checked merely because it exists, and a generated summary is not source-
aligned or scientifically accepted without separate evidence.

## Artifact classes

| Class | Git policy | Examples |
|---|---|---|
| Hand-authored authority | Track and review the source directly. | Specifications, schemas, policies, migrations, producer code. |
| Deterministic tracked derivative | Track only when review, offline use, or deployment needs the exact bytes; commit producer/input changes with it. | A demo data export with a checked-in drift test. |
| Ephemeral build or inspection output | Do not track; rebuild in a temporary or ignored directory. | `_site/`, caches, coverage output, rendered inspection files. |
| Paper/source cache | Keep outside the public tree or ignored/quarantined unless an exact rights decision permits distribution. | Downloaded arXiv archives, extracted TeX trees, publisher PDFs. |
| Released Paper Agent artifact | Store in content-addressed release storage and bind it in a replay bundle; Git may contain small reviewed fixtures only. | Exact records, formal packages, logs, graph snapshots, archive receipts. |
| Restricted or confidential artifact | Never put bytes in public Git or public CI artifacts; retain only policy-permitted metadata, digest, locator, and disposition. | Restricted source, private review identity data, secrets. |

## Requirements for a tracked generated file

A tracked generated file must have:

- a stable producer path and producer version;
- exact input paths or immutable references and hashes;
- a pinned runtime and dependency environment;
- deterministic ordering, line endings, encoding, and serialization;
- no wall-clock time, random seed, network result, machine path, or secret unless
  explicitly normalized and justified;
- one documented regeneration command;
- one no-write drift check that compares regenerated bytes;
- a clear generated marker or adjacent manifest where the format permits;
- a rights and redistribution disposition for every external input and output;
  and
- code-owner review of the producer and derivative in the same pull request.

If byte-for-byte regeneration is impossible, the artifact must instead define a
verifiable equivalence rule, record the nondeterministic fields and reason, and
be explicitly approved as an exception. It must not pass a byte-drift check by
normalizing away scientifically meaningful differences.

## Regeneration workflow

1. Verify that the working tree contains no unrelated changes to the output.
2. Reproduce the pinned environment with `make bootstrap`.
3. Run the documented producer without network access unless acquisition is the
   producer's declared responsibility.
4. Run its no-write drift check and the relevant schema/cross-record validators.
5. Inspect the semantic diff; matching JSON syntax alone is insufficient.
6. Commit the producer, exact inputs or references, output, and updated hashes in
   one reviewable pull request.
7. Run `make check`; CI must reject side effects or remaining drift.

Never “fix” a generated hash by editing only the hash field. Never regenerate
over an immutable released record. Publish a new record revision or superseding
release instead.

## arXiv and external-source rights

An arXiv page being publicly reachable does not prove that every source archive,
figure, bibliography, publisher witness, or derivative may be redistributed.
Acquisition, local processing, public redistribution, and hosted-model use are
separate permissions.

For each obtained artifact, record:

- exact work and source version;
- origin URI, acquisition time or attempt, local byte hash, and extracted-tree
  hash where applicable;
- observed license or terms and the evidence used;
- allowed processing and model-use classes;
- redistribution status, decision basis, reviewer or policy reference, and
  effective policy revision; and
- public, quarantine, restricted, withheld, or deleted/tombstoned location.

Downloaded source archives and extracted trees may be kept in a local research
cache for authorized analysis, including the repository's local reference
workspace, but they must not be newly committed or served publicly unless the
artifact has an explicit `APPROVED_PUBLIC`-equivalent disposition under the
implemented rights schema. Unknown rights are treated as not approved for
redistribution.

When bytes cannot be redistributed, public records may expose only the exact
digest, immutable source locator, rights disposition, and withholding reason
allowed by policy. An offline verifier may validate user-supplied authorized
bytes. Takedown or license change creates an append-only rights, tombstone, or
withdrawal record; it does not falsify old hashes or claim that deleted bytes
remain available.

Generated derivatives—including extracted text, normalized equations, figures,
translations, embeddings, and formal packages—need their own disposition. The
input's status does not automatically authorize the derivative.

## CI and release artifacts

- Pull-request workflows use deterministic offline fixtures and no production
  secrets.
- Live arXiv checks are separate smoke tests and cannot be a core reproducibility
  gate.
- CI artifacts have a declared retention and must not contain restricted source,
  credentials, confidential review data, or private chain-of-thought.
- A release bundle binds every included byte and every withheld-byte reference
  under exact hashes and rights dispositions.
- Software build artifacts and Paper Agent replay bundles follow different
  release gates; neither is created merely because a generated-file check passes.
