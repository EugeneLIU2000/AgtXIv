## 1. 结论

**Agent 分工基本合理；当前主要缺口在宿主的执行接口，而不是缺少更多 Agent。Neo4j 适合接入，但应是可替换的关系查询层，不能成为第二个知识写入口。**

最小闭环是：保存精确候选 → 获取相关记录 → 固定下一张工作单 → 专业 Agent 处理 → 独立审阅。数据库只负责可靠地保存、找到和追溯这些对象，不决定一个数学推导是否成立。

| 组件 | 它回答什么 | 它不能回答什么 |
|---|---|---|
| SQL 候选库与运行账本 | 哪个版本的记录存在，哪个任务交付了什么 | 不能因写入成功认定 claim 正确 |
| Git / GitHub 封存 | 哪些精确字节已经归档、远端是否读回确认 | 不是在线工作队列，也不能恢复尚未导出的更新 |
| Neo4j 派生图 | 在指定批次内，哪些依赖、推理和记录引用相连 | 路径不是证明；连接多不是数学重要性认证 |
| 专业 Agent 与独立检查 | 条件是否对应，推理是否成立，代码是否表达原命题 | 不直接修改数据库，不自己授予执行或认可权限 |

## 3. 宿主只需五个逻辑模块

“模块”是代码和权限的划分，**不是现在就启动五个微服务或调用五个模型**。

1. **任务接纳与调度。** 接纳 Planner 建议，核对最低输入、用途、独立性要求和父预算；创建不可变 Task，管理租约、重试和停止。图查询不能给子任务重置预算。
2. **候选存储。** 持有唯一业务写入口和事务；核验原字节与身份；原子保存业务记录、实际运行事件、待派生消息。图和 Git 均不能反向覆盖业务记录。
3. **身份与证据门。** 装配真实执行归属和可见性；按固定政策判断已有独立记录是否足以解除某个用途的 EVIDENCE 门。它不自己写数学评语，也不能由同一生产者冒充所有审阅身份。
4. **关系服务。** 含固定映射的 projector 和固定词汇的 query adapter。只处理经核验的本地封存批次；查询结果还要回源核对。Neo4j 是这个模块的一种后端。
5. **归档发布。** 按明确授权，将同一批精确字节写入数据仓库并读回。归档延迟不伪装成本地失败，也不伪装成已经远端备份。

这些模块共享精确引用、错误分类和运行账本，不共享不受限制的凭证。Utility 是已有固定程序操作的入口，不增加一个有独立科学判断权的“杂务模型”。

## 4. 为什么保留 Neo4j，但不把它设为启动条件

多跳依赖查找、某个上游变化后的潜在影响范围、选定证明路线的结构展示，适合用关系查询表达。保存文件、获取论文、生成 claim、登记任务和执行审阅则不需要先启动图数据库。

第一版查询接口只支持三种问题：**依赖邻域、选定路线的推理步骤、原记录的精确引用邻域**。论文全文搜索、向量相似度、自动发现定理等不混进这个接口。未来的中心性或模式挖掘，应先生成有来源、有覆盖说明的研究建议，再进入正常的生成与审阅链。

图只是指定历史批次的地图。它不能证明“这是最新状态”“没有反例”“没有上游”或“可以直接继承 Lean code”。形式复用仍需现有的用途决定、精确环境、声明及实际兼容性检查。
