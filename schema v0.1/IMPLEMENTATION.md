# 交付边界与后续开发顺序

## 1. 本轮要完成的事情

用户目标是建立 `schema v0.1/`，规范多 agent 最小接口并完成底层系统规划，尤其是 Neo4j 与 GitHub repo 的分工和讨论。**不是本轮部署全部 agent、迁移数据库或完成真实论文的科学验证。**

| 要求 | 交付位置 | 验证方法 |
|---|---|---|
| 独立的新目录，保留旧业务含义 | README、compatibility.lock.json、COMPATIBILITY | 新包只引用 v0.0；校验实际旧 bundle 身份和 64 种类型 |
| 每个 agent 最小输入、输出、原则、停止与交接 | AGENT-CONTRACTS、agents.json | 9 种工作模板、23 项操作；操作唯一，所有业务短类型确实属于 v0.0 |
| 可调用的共同接口 | task/result/common/agent-registry schema | 合法样例与越权类型、未知字段、错误版本、错绑目标等反例 |
| 明确 agent 工作顺序 | SCHEDULING | 依赖与证据门、并行、范围变更、预算、重试、局部阻塞有规范；离线工作图检查无环和完整前置引用 |
| 数据格式固定，杂务不另用模型决策 | Utility 操作与 STORAGE | 模型不获得数据库写权，组包/校验/保存/投影由固定程序负责 |
| SQL 运行与候选存储 | STORAGE、storage/runtime.sql | DDL 在空 SQLite 内实际执行；约束与非法操作测试；现有 V3 业务表不重复创建 |
| GitHub repo 格式、封存与恢复 | STORAGE、archive-batch schema | 完整批次字节/引用检查、非覆盖封存协议、失败恢复和大附件边界 |
| Neo4j 结构与 Docker 规划 | STORAGE、storage/neo4j*.cypher、compose.example.yaml | 依据官方文档核对；静态参考。未在 Docker/Neo4j 中执行，不宣称部署成功 |
| 旧 schema 复用与缺口 | COMPATIBILITY | 业务记录归属映射，已定义/已有本地机制/待接通分开 |
| 可读性与工程反方检查 | 多 agent 独立审阅，结果见 VALIDATION | 不用任务完成替代科学成立；检查主线清晰与接口遗漏 |

`validate.py` 是有界离线参考检查器，不是生产认证器。`valid=true` 只表示所报告范围的检查通过。

## 2. 哪些真的能运行

当前可运行：旧契约 pin 核对、本包 JSON Schema 离线解析、操作输入/输出白名单、最小直接输入检查、任务精确目标与可见输入声明绑定、声明回避名单、工作图结构检查、候选导出字节及批内引用闭包校验，以及 SQL 参考 DDL 的本地测试。

以下仍需后续实现，不能靠更多 schema 字段替代：

- 真正的模型调用和 paper/proof/dependency 语义生产者。
- 运行队列、任务领取、预算扣留、租约回收、幂等重试及取消。
- 实际执行身份、生产参与者闭包、权限隔离和反向解释的可见内容控制。
- 目标级 EVIDENCE 判断及有条件结果的安全复用。
- V3 业务记录与 outbox 的同事务接入、Git 导出器和远端读回核验。
- 完整 Neo4j 导入器，包括全部上下文、规则、证据、路线和冲突映射及就绪门。
- 独立 Lean 检查、实际声明/公理检查、原文对齐及需要的科学审阅。
- 正式发布、科学准入、生产容量、故障恢复和真实两论文验收。

离线操作最低输入检查仅覆盖能从工作单直接判定的必要条件；包内引用的具体数学条件、各类审阅的完整证据组合和所有规范权限仍由 v0.0 校验及未来受控运行/科学审阅承担。不能把白名单允许某类输入误解为这类证据已经足够。

## 3. 接下来按什么顺序开发

### 第一步：实现单个可恢复工作单

接入固定 Task 与真实 Result 捕获，保存精确 task 字节、模板/配置/模型/代码身份和所用规则。先使用无科学声明的测试 handler 验证领取、超时、回执、重试与恢复，再接真实 Paper 操作。

验收：重启后知道哪些任务交付、哪些等待；相同输入重送不重复记账；迟到 worker 不能覆盖新 attempt；不能只改 principal 字符串骗过独立性要求。

### 第二步：接一条 claim 的实质工作链

来源取得 → Paper 原文与数学拆解 → 独立确定范围 → Proof 与 Dependency 按缺口协作 → 独立审阅处置。每个节点都能保存、重新读取和继续；缺内容保留缺口而不是填假记录。

验收：读者能从结果追到原文字节、假设、共同前提和未解项。优先补真实语义工作，不以全文词法命中数代替科学主张数。

### 第三步：接入原子候选保存和封存

为现有 LocalStore 加入受控事务边界，让业务记录、运行事件和 outbox 一起提交；实现 self-contained 批次导出、离线验证、Git commit/push 后精确读回核验。网络动作不在 SQL 长事务里执行。

验收：在 SQL commit 后、Git commit 后、push 后、回执写入前分别中断，都能恢复且不覆盖旧身份；未封存 SQL 数据有备份恢复边界。

### 第四步：构建可重建的 Neo4j 图

实现完整映射和批次隔离。只在精确集合、共同前提、路线与闭包全部检查后切换可见头。以批次哈希、投影程序版本和视图选择固定派生结果。

验收：丢弃图投影后，从指定 Git 批次重建得到同一逻辑节点/边集合；不得从多个批次拼接出不存在的证明；候选图不成为正式准入图。

### 第五步：按需接形式化，并用两篇真实论文验收

已有合适声明先复用；缺少时生成形式代码并独立运行检查、反向解释和对齐。比较一项真正通过用途检查的复用和一项因条件不匹配被拒绝的复用，再做一次上游修订与局部重审。

验收：能说明节省了哪段实际工作、仍承担哪些假设、拒绝复用的具体原因。未测量成本节约时不宣称低价模型一定足够；低成本模型先用于已有评测覆盖的操作。

## 4. 以后演进契约的规则

当前包是实验版。运行宿主必须把模板目录、JSON schemas、提示配置、处理规则、代码与模型设置的实际字节身份纳入每次 attempt 的输入清单，不能只记录目录名或 `0.1.0` 字符串；`runtime_attempts.input_manifest_sha256` 为这份受控清单预留绑定位置。

字段含义、输出权限或调度规则改变时，发布新契约版本并保留旧解释器/迁移说明。已有任务字节和业务结果不回写。当前 v0.0 的 pin 变化会让离线检查失败；必须显式审阅兼容性后更新，不允许运行时自动追随最新版。
