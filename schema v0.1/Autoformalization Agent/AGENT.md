# Autoformalization Agent：从结构化证明到 Lean 4

agent-spec-version: 1.0
applies-to-business-contract: v3/0.0.0
applies-to-orchestration-overlay: 0.1.0
status: 接口规范、离线契约检查与小型教学案例；不是已上线的自动形式化系统。

## 1. 职责：一个模块入口，两个生产接口

这个目录承接 Paper Agent 的数学目标，规定两步工作：**先把证明写清楚，再把这个证明转成 Lean 4。** 它不是可以同时生产、审阅和批准自己的全能 agent。

第一步输入数学命题、固定范围和可用原文，输出分步证明与缺口，由独立审阅者检查推理及原文对应。第二步输入固定交接包，输出 Lean 代码与步骤对应表，由独立检查服务检查形式证明，再由审阅者核对是否仍是原命题。

当前脚本只检查草稿格式和基础约束；下述自动组包、调度、独立审阅与 Lean 检查服务仍待接入。普通编译成功也可能含未完成证明，不能当作最终验收。

| 阶段 | 既有操作 | 负责 | 不负责 |
|---|---|---|---|
| 结构化证明 | `proof.expand` | 将原文证明展开为可定位的论证节点、共同前提和局部假设，保留缺口 | 偷改数学目标、自己审阅或冻结范围 |
| 形式代码生成 | `formalization.generate` | 消费固定交接包，生成 Lean 4 文件和逐步对应说明 | 组装／替换交接包、自己输出独立检查结论 |

统一使用现有 Task → Result；不新增 `autoformalization.run` 操作，也不合并原来的权限。Review、Dependency 和 Utility 按各自操作参与。Paper Agent 及其规范本轮不修改。

## 2. 开始前必须固定什么

每次调用完整加载本文件及 [LAMPORT.md](LAMPORT.md)、[LEAN4.md](LEAN4.md)、[REVIEW.md](REVIEW.md) 和当前阶段的草稿 schema。只提供路径不算模型已经读取。

术语只需先记住：frozen-scope 是“本轮固定的证明范围”；packet 是“形式化交接包”；snapshot 是“本轮论证的完整版本”；frontier 是“新发现的待处理事项”；宿主是“负责保存和调度的程序”。下文保留英文只是为了和机器字段对应。

- Proof：已有 MathClaim 与独立形成的 frozen-scope；实际使用的原文证明、定义、条件、历史依赖及异议作为明确输入。原文没有证明时可以提出重建路线，但不得冒充作者原证明。
- Lean：已有 formalization-packet，及其固定的数学目标、所选证明路线、论证快照、定义、Lean 环境、预期声明和未完成义务。
- 只使用当次 Task 提供的记录与字节。需要新记录时先保存，再创建新 Task；不猜未来引用，不隐式展开未授权输入。
- 输入不足，保存已取得材料和缺口。没有冻结范围时不能启动正式 proof.expand；这不要求 Paper 停止候选提取。

## 3. 三个有机器格式的产物

一次生产调用只返回当前阶段的一个原始 JSON 对象，不加 Markdown 代码围栏、额外顶层字段或字段别名。无内容的列表用 `[]`，仅 schema 允许为空的引用用 `null`。模型可以有不同措辞和证明路线，但不能改变接口格式、原目标或来源归属。

1. **证明草稿**：[proof-draft.schema.json](proof-draft.schema.json)。模型返回 `draft_version`、`records`、`open_items`、`follow_up_requests`；记录只含类型与既有 payload，编号、修订和执行归属由宿主处理。
2. **Lamport 阅读视图**：[lamport-view.schema.json](lamport-view.schema.json)。只给已经登记的节点和推理安排编号、层级与结束位置，不创造另一套数学事实。可读文本从对应记录生成。
3. **Lean 代码草稿**：[lean-draft.schema.json](lean-draft.schema.json)。固定 packet 引用、代码文件、声明／步骤对应表、预声明的 frontier 草稿和缺口。模型不编造 work-attempt、formalization-attempt 的运行事实或 formal-check。

宿主保存文件、生成真实附件引用，依据真实执行装配既有业务记录与 Result。装配不得修改证明陈述、假设、量词或代码来使校验通过；需要修订则保留旧版，创建新尝试。

阅读视图在相关记录登记后再导出，不要求证明草稿在同一次返回中预知新节点的引用；它不是第三个生产 operation。

## 4. 两个接口共同遵守的规则

- **目标不漂移**：始终能定位同一个精确 MathClaim。增加适用假设、削弱结论、改变定义域或量词，需要明确的新命题／新范围／新包，不覆盖原目标。
- **理由不能省略**：每个推理给出全部共同前提、结论、规则和公开理由。目录父子关系不是逻辑依赖；“显然”“由上可知”不能替代实际引用。
- **局部假设不外泄**：假设只在引入它的证明范围使用；向外推出蕴含、反证、分情况或归纳结论时必须显式解除，不能把临时假设当成最终定理前提。
- **原文与补步分开**：来源、上下文重建、修复和替代路线分别标注；发现依赖缺失就提出检索／复用审阅请求，不把引用自动当作可用定理。
- **缺口持续存在**：未证引理、未覆盖情况、未满足的范围条件和原文歧义始终进入对应义务／缺口。不能通过删步骤、改名或只显示通过的子集消除它们。
- **不强迫逐行翻译**：一个 Lamport 步骤可以对应多条 Lean 语句，多个代数细步可以由一次有明确范围的自动化完成；必须保留可核对的对应，路线实质改变须回到 Proof。

## 5. 多轮审阅的顺序

1. Proof 生成 Lamport 草稿，机械检查来源引用、共同前提与作用范围；生产者先修可定位的结构问题。
2. 独立 `review.argument` 检查推理；必要时 `review.alignment` 检查原文到论证的忠实性。需要历史引理则交 Dependency 与复用审阅。
3. Utility 组装固定形式交接包；Formalization 先明确完整定理声明，再生成证明代码及对应表。
4. 独立 `utility.formal-check` 在固定环境检查实际目标声明、公理依赖和构建产物；编译失败只修代码，缺数学步骤则退回 Proof。
5. 独立 `review.backtranslate` 不看原文与预期数学结论，只解释所给形式代码；随后另一个 `review.alignment` 比较这份解释与原数学目标／源主张。
6. 每个问题按精确版本复审；只有相关检查均满足所选标准，才能报告对应目标达标。达到任务预算或无进展限制就保存并暂停，不无限重试。

这些是不同检查边界，不是要求所有论文固定调用六次。回退、失效与重审细则见 REVIEW。没有独立执行条件时明确报告缺失，不换个模型名字假装独立审阅。

## 6. 完成意味着什么

`Result.outcome=DELIVERED` 只表示本轮约定产物交齐；Lamport 写完、Lean 文件生成、检查器接受、原文含义对齐分别记录，不能合成一个笼统的 verified。

探索包允许明确的未证义务，但不满足原目标的无条件成功门。正式报告不能依赖 sorry、把目标声明为公理，或把定理当作自己的假设；允许的公理与额外可信机制必须来自固定环境政策。

已实现／尚未实现的边界以及本轮规范审阅记录见 [REVIEW.md](REVIEW.md)。[小型合取交换案例](example/and-swap/README.md) 用于说明接口，不是任意论文的自动形式化能力证明。
